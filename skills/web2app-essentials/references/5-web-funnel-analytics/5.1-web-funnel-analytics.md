# Web Funnel Analytics

*Distilled from course module 5.*

## Summary

Analytics for a quiz-to-paywall web funnel splits into three layers: **product analytics** (event tracking, funnel conversion, dashboards), **marketing analytics** (spend vs ROAS, UTM standards, attribution), and **financial planning** (a revenue model that turns historical data plus assumptions into a revenue and payback forecast). The single most important report in the whole system is **Spend vs ROAS by cohort** — how much you spent on a cohort of users vs how much you will earn from it. Everything else exists to explain and improve that number.

## 1. Product analytics

### Tools

Any solid product analytics stack works:

- Amplitude
- Mixpanel
- Google Analytics (GA4)
- In-house BI

### Onboarding event taxonomy

Instrument the funnel with this event set. Fire events on *display* of screens, not just clicks, so you can measure drop-off precisely.

| Event | Properties | Trigger / description |
|---|---|---|
| `onboarding started` | — | First screen shown |
| `2nd screen` | — | Second screen shown (early-dropoff signal) |
| `screen completed` | `screen id`, `input` | Each screen completed, passing along the user's answer/input |
| `registration` | — | Registration / email-capture screen shown |
| `paywall` | `paywall id` | Paywall shown |
| `purchase` | `product id`, `price`, `payment method` | Successful purchase: main subscription, subscription upgrade, or upsell |
| `app download click` | — | Click on "download the app" / "create account" button |
| `app sign in` | — | Login inside the app (closes the web-to-app loop) |

### Payment event taxonomy

| Event | Properties | Trigger / description |
|---|---|---|
| `checkout view` | — | Checkout displayed |
| `purchase click` / `purchase started` | — | Click on the pay button |
| `purchase` | `product id`, `price`, `payment method` | Successful purchase (main subscription, upgrade, upsell) |
| `purchase failed` | `error message`, `product id`, `price`, `payment method` | Payment attempt failed |
| `subscription renewal purchase` | `product id`, `price`, `payment method` | Renewal charge succeeded |
| `subscription renewal fail` | `product id`, `price`, `payment method` | Renewal charge failed |
| `subscription canceled` | `product id`, `price`, `payment method` | Subscription canceled |
| `subscription refunded` | `product id`, `price`, `payment method` | Subscription refunded |

### User properties

Attach these to every user so any report can be sliced by them:

| Property | Why |
|---|---|
| `userid` | Same id for web and app sessions — this is what stitches the web funnel to the app |
| `email` | If email is used for login |
| `web_url` | URL of the web funnel — essential when you run many funnels |
| `version` | Funnel version, bumped on every release — invaluable for debugging regressions |
| `utm_source`, `utm_campaign`, `utm_term`, … | Marketing attribution |
| Inputs from each onboarding screen | One property per screen — enables segmenting by user answers |
| Demography | geo, age, gender |
| Technical | device OS, browser, device model, device language |
| A/B test flags | One property per experiment, holding the assigned variant |

### Core dashboards

Run two levels of dashboards:

**Macro level — long-term trends**
- Data range: 12 months; granularity: monthly/weekly
- Charts/tables:
  - Spend vs predicted ROAS
  - LTV (day 0, 1 year) vs CAC
  - Revenue (gross, net)
  - Revenue (new vs repeat)
  - Renewal rate by monthly cohorts
  - CR onboarding → purchase, by country/channel/etc.
  - Refund rate

**Micro level — daily operational reports**
- Data range: 30–60 days; granularity: daily (sometimes hourly)
- **Marketing monitoring:** plan vs actual (revenue, spend, new users); spend vs ROAS end-to-end, broken down by country/funnel/source; traffic structure and quality; movement vs yesterday / last 7 days
- **Web funnel monitoring** — the conversion ladder:
  - CR: start onboarding → purchase
  - CR: start onboarding → 2nd screen
  - CR: start onboarding → paywall
  - CR: paywall → purchase
  - CR: purchase → upgrade
  - CR: purchase → upsell
  - CR: purchase → app download click
  - CR: app download click → sign in
- **Monetization monitoring:** ARPPU day 0, ARPU day 0, ARPU 1 year; purchases by payment method and plan; refund rate; billing issues

### Standard report types

1. **Metric dynamics / growth metrics** — revenue, purchases, traffic over time. Granularity from year down to hours; sliced by geo, funnel, gender, ad source, and segments built from quiz answers. Revenue additionally split by payment method, plan, and new vs repeat.
2. **Conversion reports** — every step of the ladder above, plus post-purchase conversions (purchase → cancel/refund/dispute, purchase → renewal). Always define an explicit **conversion window** (X minutes/hours/days).
3. **Funnel reports** — the same steps rendered as a funnel, same slices and windows.
4. **Retention reports** — purchase → renewal, purchase → cancel, purchase → product activity; by cohorts and the same slices.
5. **Tables** — flat and pivot tables with many metrics across slices for ad-hoc analysis.

## 2. Marketing analytics

### The most important report: Spend vs ROAS

- Per cohort: how much you spent vs how much you will earn from that cohort of users.
- Shows the whole funnel in motion, from impression to conversion.
- Enrich it with intermediate conversions, product metrics, and traffic-structure fields (e.g. % male/female, average BMI for a fitness funnel).
- Must support drill-down: by source → campaign → creative.

### UTM tagging standard

Tag **all** ads with UTM parameters following one fixed convention. Example:

- `utm_source` = ad network
- `utm_campaign` = campaign name
- `utm_content` = ad-group name or creative name
- `utm_term` = `[campaign_id]_[adset_id]_[ad_id]`

**Tip:** always pass raw IDs (in `utm_term` or similar) and map on IDs, not names — names get renamed and contain manual typos. Custom parameters work just as well as UTMs if you prefer.

### Mapping ad spend to internal data

1. Store UTM tags (campaign/creative IDs) on each `user_id` and forward them into product and financial analytics.
2. Pull spend data per campaign/creative ID from the ad platforms.
3. Pull product and financial data per the same IDs from your analytics.
4. Join everything at the campaign/creative-ID level: ID → spend (ad platform) → purchases and revenue (product analytics).

Services that automate the ad-platform ingestion: **Funnel, Improvado, Fivetran, Supermetrics**, and similar.

### Choosing an attribution model

CAC per channel/creative depends on the attribution model:

- **First visit** — purchases credited to the UTM tags of the user's first visit
- **Last visit** — credited to the last visit
- **Last visit with purchase** — credited to the visit during which the purchase happened
- Complex models — linear, weighted, ML data-driven
- Promo-code attribution

**Recommendation for web funnels: use last visit with purchase.** The attribution error is not critical because:
- the quiz is long and users complete it deliberately;
- there are few repeat touches: <1% overlap between ad sources, and ~95% of purchases happen on day one.

>    Ad accounts Meta categorizes as health & wellness lose custom
>    parameters and URL-path data by default, and restricted tiers block
>    mid/lower-funnel events (purchase, conversion) — equally for browser
>    Pixel and Conversions API, so CAPI is not a workaround
>    ([Foley Hoag](https://foleyhoag.com/news-and-insights/blogs/security-privacy-and-the-law/2025/january/meta-s-new-advertising-rules-key-considerations-for-health-and-wellness-businesses/)).

>    Manager and may need to optimize on upper-funnel or on-platform
>    events.
> 4. **Google Tag Gateway (GA May 2025).** Google tags served first-party
>    from your own domain via Cloudflare reverse proxy — one-click, free —
>    bypassing ad blockers and third-party script restrictions; Google's
>    beta reported an **average 11% improvement in data signals**
>    ([Cloudflare](https://blog.cloudflare.com/google-tag-gateway-for-advertisers/)).
>    The cheapest server-side-tagging-adjacent win for a funnel team.

### Unattributed ("organic") store installs

- Not everyone buys immediately or even clicks the ad (some users screenshot a TikTok ad and come back later).
- Returners land either directly on your site (check what they search for, what they see, and where your site redirects) or directly in the App Store / Google Play.
- **5–15% of revenue/ROAS** typically arrives through these unattributed store installs — your real ROAS is 5–15% better than measured. They are "organic" in name only: they disappear if you turn the web-funnel ads off.

How to measure the share:
- Statistical modeling: toggle ads on/off and watch install dynamics; geo-lift tests (ads on in one region, off in another) and compare.
- An in-app onboarding survey ("How did you hear about us?") — answer accuracy is roughly 80–90%.

## 3. Financial planning

The goal is not to observe the Spend-vs-ROAS fact but to **forecast the outcome of marketing and product decisions** before making them.

**Model inputs:**
- Historical data
- Marketing assumptions: spend per channel; expected CPM, CTR, CPC, CR, CPA; number of customers acquired
- Product assumptions: which plans customers buy, conversion to upgrades/upsells, prices, renewal (retention) behavior, refunds, and payment commissions

**Model outputs:**
- Revenue forecast and plan, split into revenue from new vs existing users
- Payback point and profitability point

The course ships an xlsx template for this model (see `5.2-revenue-model-template.md`). Adapt it per project: platforms (web, iOS, Android), segmentation (geo, plans, individual funnels), extra metrics and detail.

**Plan-vs-fact report:** run a daily report comparing plan to actuals; the forecast for the period is recomputed from current actuals plus the days remaining until the end of the plan.
